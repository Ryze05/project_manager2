## Product summary (from the spec)

Collaborative project manager: projects with members and roles, tasks/subtasks on a 3-column board (por hacer / en curso / hecha), comments, and a personal "mis tareas" view. A solo project is just a project with one member.

Planned stack: NestJS (TypeScript, one module per feature: auth, projects, tasks, comments) + Next.js front-end styled with CSS Modules (Tailwind was proposed in the spec and rejected), REST API with JWT, PostgreSQL + Prisma, bcrypt, class-validator, Swagger. DB/ORM/front-end libs are marked "propuesta" (not yet confirmed).

Built in levels; do not start a level until the previous one works and is reviewed:
1. Core (build order: auth/projects/members → tasks & board → subtasks → comments → mis tareas; if time is short, cut from the end)
2. Added value (labels/filters, activity log, drag & drop with stored position, invitations, metrics, archiving, ownership transfer, refresh tokens…)
3. Extras (read-only role, notifications, realtime, attachments, e2e tests). **Added by the user (not in the spec): email sending**, starting with a notice to the invited person when they get an invitation (today they only see it inside the app); the spec's notifications are in-app only. It also unlocks inviting unregistered emails.

## Architecture and business rules that span modules

- **Data model: 5 entities** — User, Project, ProjectMember (composite key user+project, role owner/member), Task, Comment. Subtasks are Tasks with a nullable `parent` field (no separate table). All entities share the same ID type.
- **Validated in the service layer, not the DB:** assignee must be a project member; a subtask cannot have subtasks (one level only).
- **Subtask progress (e.g. 2/4) is computed from subtask states, never stored.**
- A task cannot be marked done while it has pending subtasks; creating/reopening a subtask under a done parent sets the parent back to "en curso"; the parent is never auto-completed (decided twice: it was briefly automatic and was reverted, because the responsible reviews and closes the task, as in Asana/Jira; the detail page only shows a "Todas las subtareas están completadas" hint with a button; an opt-in per-project setting would be a level-2 candidate).
- Level 1: a subtask cannot be moved to another parent nor can a task be converted to a subtask (level 2 lifts this).
- Level 1: exactly one owner per project; the owner cannot leave or be removed (only delete the project). Level 2 replaced this with several owners (see "Several owners").
- Removing a member leaves their tasks/subtasks unassigned. Deleting a task cascades to subtasks and comments; deleting a project cascades to everything.
- Non-members cannot see anything about a project. Owners invite people by email, only already-registered users (clear error otherwise); they join by accepting (level 2: see "Invitations"; level 1 added them directly).
- Permissions: owner and member both create/edit/move tasks and comment; members delete only tasks/subtasks they created and only their own comments; owner deletes any task/comment; only owner manages members and edits/deletes the project. Comments are editable only by their author.
- Auth: password min 8 chars with one uppercase and one number; JWT valid 24h (level 1).
- Board: subtasks never appear as cards, only inside the parent; cards in a manual order (drag and drop, level 2; before that: priority, then due date). "Mis tareas" is ordered by due date, shows pending + in-progress by default (toggle for done), and shows project and parent task for subtasks.
- Out of scope: nested subtasks, extra roles, external integrations, mobile app, checklists.

Note: the spec has a few level-1 vs level-2 differences (single vs multiple owners, no moving subtasks vs allowed) — implement the level-1 behavior first and keep the code open to the level-2 changes.

## Frontend (`frontend/`)

pnpm project, **Next.js 16** (App Router, `src/`), React 19, TypeScript, **CSS Modules** (no Tailwind), zod. Its `AGENTS.md` says this Next.js has breaking changes: read the guides in `frontend/node_modules/next/dist/docs/` before writing Next code. Facts already learned from them: `middleware` is now **`proxy.ts`**; `cookies()` is **async** and can only set/delete cookies from a Server Action or Route Handler.

Commands (from `frontend/`): `pnpm dev` (port 3001), `pnpm build`, `pnpm start`, `pnpm lint`, `pnpm typecheck`. Env: `frontend/.env` (gitignored; `.env.example` is the template) holds `API_URL` (default `http://localhost:3000/api/v1`), server-side only.

- **The browser never talks to the API.** Everything goes through `src/lib/api.ts` (`import "server-only"`), called from Server Components and Server Actions. It adds the Bearer token, never throws for HTTP or network errors and returns `{ ok, status, ... }` (status 0 = API unreachable). Nest validation errors (`message` as an array) are joined into one string. A non-JSON body (an HTML 502 from a proxy) is tolerated, and paths with `..`, backslashes or encoded slashes/dots are refused (400) because ids reach Server Actions from the client.
- **Session = the API's JWT in an httpOnly cookie** (`src/lib/session.ts`: `getToken`, `setToken`, `clearToken`; `sameSite: lax`, `secure` in production, 24h like the JWT). Client JS never sees it. `src/proxy.ts` only checks that the cookie exists (no cookie -> `/login`; cookie on `/login`/`/registro` -> `/proyectos`); an expired token is rejected by the API (401) and `/sesion-caducada` (route handler) clears the cookie and goes to the login. That route is a GET, so it only clears the cookie after asking the API (`/auth/me`) and getting a 401 (a valid session just returns to `/proyectos`), otherwise any site could log users out with a link.
- **Forms:** Server Actions + `useActionState`, validated with zod in the action. zod only mirrors simple rules for instant feedback; the API stays the source of truth and its errors are always shown.
- **`cacheComponents` / `partialPrefetching` are off** on purpose: the scaffold enabled them, but nearly everything is per-user and must be fresh, and they force `<Suspense>` around every `cookies()` read. Fetches use `cache: "no-store"`.
- **Styling and design system:** the agreed look is saved as an 8-screen HTML prototype in `docs/diseno/sistema-de-diseno.html` (Sistema, Acceso, Inicio, Proyectos, Tablero, Detalle, Mis tareas, Miembros); its `:root` is what `src/app/globals.css` holds. Light only, no dark mode. Rules: 3 colour families (warm neutrals, one purple accent `--accent`, terracotta `--danger` only for overdue / high priority / errors); `--accent-soft` is the single purple tint for hover, selection, initials and role, `--accent-mid` for counters over it; 4 px spacing scale (`--s1..--s7`, page 32, card 24, gap 16, block 32; 16 on mobile); radii 8/12/20/pill; one shadow, one `--scrim` for modal backdrops; 7 font sizes, 3 weights. CSS Modules must only use these variables (no raw colours, spaces or radii). The prototype may change as screens get built; keep both in sync.
- **Base components** (`src/components/ui/`, import from `@/components/ui`): `Button` (primary/ghost/danger/link), `Card`, `Badge` (neutral/accent/danger/outline, optional dot), `Avatar` (initial; person or project; one colour variant), `Input` (label/hint/error, optional `adornment` inside the field), `PasswordInput` (Input with a show/hide eye button), `ProgressBar`. `Textarea` (grows with its content via `field-sizing`, `rows` = minimum) and `ButtonLink` (a link that looks like a Button) are also there. The sidebar lives in `src/components/Sidebar/`; `Select`, `Segmented` and `SwitchLink` (segmented control and on/off switch made of links, so their state lives in the URL) are also there; `Modal` (`src/components/Modal/`, native `<dialog>` driven by an `open` prop; children mount only while open, so a form inside starts clean each time), `AvatarStack` (overlapping initials, "+N" after 3; used on board cards for the subtask assignees), `TaskCheck` (`src/components/TaskCheck/`) is the done/pending check box of a task or subtask.
- **Server Actions** use the helpers of `lib/actions.ts`: `callApi` (like `api()` but a 401 sends the user to `/sesion-caducada`, so no action repeats that check; login/register use plain `api()`), `formText` and `fieldErrors` (zod messages per field).
- **Failing actions do not crash the page:** Server Actions that can be refused by the API (delete, remove member, move/check a task, edit a comment) return `{ error }` (`ActionResult` in `lib/types.ts`) and the client shows it in place (inside the `ConfirmDelete` dialog, next to `TaskCheck`, under the status select). Throwing is only for Server Components via `unwrap()`. Actions that change what the layout shows (sidebar projects, pending counter, member counts) call `revalidatePath("/", "layout")`.
- **Layout:** every signed-in screen lives in the `(app)` route group, whose layout fetches `/auth/me` and `/projects` for the sidebar; `(auth)` has its own layout without it. Server Components read through `lib/queries.ts` (`getMe`, `getProjects`, `getProject`, `getBoard`, `getTask`, `getComments`, `getMyTasks`...: React `cache()` makes the layout and the page share one request per resource, and they already `unwrap()`), and pages ask for everything they need in one `Promise.all`; `unwrap()` lives in `lib/api.ts` (401 -> `/sesion-caducada`, 404 -> not-found, else error boundary). Project routes: `/proyectos`, `/nuevo`, `/[projectId]`, `/[projectId]/editar` (owner only; also holds delete, confirmed in a native `<dialog>`), `/[projectId]/miembros` (everyone sees it; add/remove only for the owner). Clearing a description sends `null` on PATCH (an empty string would be stored as "").
- **Board and tasks:** `/proyectos/[projectId]` is the board; task routes live under it (`/tareas/nueva`, `/tareas/[taskId]`, `.../editar`). A new subtask is created from a modal on the task detail (`NewSubtaskButton`: the same `TaskForm` as a new task, with title, description, priority, date and assignee), through `createSubtaskAction`; `TaskForm` takes `cancelHref` (page) or `onCancel`/`onSaved` (modal). **The task detail is its own page, not the side panel of the prototype** (decided: simpler, works on mobile, room for comments); it serves tasks and subtasks alike (a subtask page links back to its parent and has no subtask section). Delete is shown to the owner and to the task's creator, via the shared `ConfirmDelete` (`src/components/ConfirmDelete/`). Moving a card or changing a status goes through `moveTaskAction` and shows the API's error (e.g. 409 pending subtasks); `PriorityBadge` is shared by card and detail. Comments live in `tareas/[taskId]/comments/` (thread under the detail, for tasks and subtasks alike): edit is author-only, delete is author or owner, like the API; times are formatted on the server and passed down as strings so server and browser agree.
- **Mis tareas:** `/mis-tareas?agrupar=proyecto&hechas=1` (both options optional, kept in the URL). It reads `GET /me/tasks`; "por fecha" groups by urgency (Vencidas / Hoy / Próximos 7 días / Más adelante / Sin fecha / Hechas, via `dueBucket` in `lib/format.ts`; empty groups are hidden), "por proyecto" groups by project (the one with the most urgent task first); both keep the API's order inside each group. A summary line ("1 vencida, 1 para hoy y 2 en curso") sits under the title. Each row is one big link (stretched title), like the board cards. A subtask row is marked with "↳" and "en «parent»" (a link to the parent, above the stretched row link); a task with subtasks shows "2/3 subtareas". The list stays flat on purpose (checked against Asana/Todoist: their personal lists are flat too, and the recurring request is to name the parent); collapsing a task's own subtasks under it is a possible later step. The sidebar shows the count of pending tasks (the layout fetches the default listing). `moveTaskAction` revalidates the whole layout so board, detail, mis tareas and the counter stay in sync.
- Build order (same spirit as the backend): skeleton -> tokens + base components -> register/login + redirect -> projects -> members -> board (move between columns) -> task detail with subtasks -> comments -> mis tareas. Level 2 (in progress): subtask assignee initials on cards, labels + board filters (see "Labels and filters"), the activity history (see "Activity history") and drag and drop (see "Drag and drop") and archiving (see "Archived projects") are done.

## Labels and filters (level 2)

- **Backend** (`src/labels/`, `LabelsModule` imports `MembersModule`): labels belong to a project, **no colour** (the design system has a single accent), name unique per project ignoring case (409), max 30. Routes `GET|POST /projects/:id/labels`, `PATCH|DELETE .../:labelId`. Any member lists and creates; **only the owner renames or deletes** (deleting only takes it off the tasks: implicit many-to-many `Task.labels`). A label id of another project is a 404. Each label view has `taskCount`.
- **Tasks**: `labelIds` on create/PATCH (`ArrayUnique`, max 20, `ValidateIf` so `null` is a 400). On PATCH the list **replaces** the labels, `[]` clears, omitted leaves them. Labels of another project -> 400; **subtasks carry no labels** (400). Every `TaskView` has `labels [{id,name}]` sorted by name.
- **Board filters** (`BoardQueryDto`): `label` (repeatable, OR), `assignee` (user id or `none`; a user id also matches tasks that have a subtask of theirs), `priority` (repeatable, OR), `due` = `overdue` (not done) | `week` (today + next 7 days, UTC days) | `none`. Different filters are ANDed. Invalid values are a 400. Tests: `test/labels.e2e-spec.ts`.
- **Front-end**: filters live in the URL (`lib/board-filters.ts`: `parseFilters` drops invalid values so a hand-edited URL never gives a 400; `toQuery`). `BoardFilters` is a plain GET form (selects + label capsules), no client JS; the label capsules (`LabelPicker`, native checkboxes) are reused in the task form. `LabelList` shows neutral capsules on cards and in the detail. In `TaskForm`, the `labels` prop turns the label field on (subtasks do not pass it): ticked labels go as `labelId`, new ones typed in `newLabels` (comma-separated) are created by the Server Action (matching existing names ignoring case), and a hidden `hasLabels` tells the action the form has labels (without it labels are left alone). Rename/delete live in a card on the project's edit page (`LabelManager`, owner only). Board filter for a person is a single select even though the API takes several priorities.

- **Future improvements for labels** (checked against Trello, GitHub, Linear, Jira; not decided to build): (1) colour from a short palette (5-6 tones, needs extending the design system; most apps have it, Jira does not), worth it once a project has many labels; (2) a starter set (e.g. Bug, Mejora, Urgente) when a project is created, as GitHub does; (3) the current permissions (any member creates, only the owner renames/deletes) are deliberately stricter than Trello's, where a member deleting a label stripped it from dozens of cards.

## Activity history (level 2)

- **Backend** (`src/activity/`): `GET /projects/:id/activity?taskId=&cursor=&limit=` (newest first, any member, default 50 / max 100, cursor = id of the last event received, `nextCursor` null on the last page; a cursor from another project is a 404). **Writing is not a service but the plain function `recordActivity(tx, entries)`** (`activity.ts`), called by Tasks, Comments and Members inside the same `$transaction` as the change (no change without record nor the reverse); `ActivityModule` only reads, because it imports `MembersModule` and a Members -> Activity import would be a cycle.
- **One event per field changed**, computed by `taskChanges(before, after)` comparing the rows (sending the same value records nothing). Types: `TASK_CREATED/DELETED`, `TITLE/DESCRIPTION/STATUS/PRIORITY/DUE_DATE/ASSIGNEE_CHANGED`, `LABEL_ADDED/REMOVED` (one per label), `COMMENT_ADDED`, `MEMBER_ADDED/REMOVED`. A done parent sent back to IN_PROGRESS by a new/reopened subtask is recorded as a `STATUS_CHANGED` on the parent. The description and the comment text are **not** copied (only that they changed). Not recorded: comment edit/delete, label rename/delete, project edits, tasks unassigned by removing a member.
- **A task's history** (`?taskId=`) is its own events **plus, for a parent, the creation and completion of its subtasks** (events carry `parentId`, without FK too; completion = `STATUS_CHANGED` with `data.to = DONE`). Everything else of a subtask (priority, date, comments...) stays in the subtask's own history. Checked against Jira/Asana/ClickUp: they keep them apart and users keep asking for exactly this.
- **`Activity.taskId` has no FK on purpose** and the title is stored (`taskTitle`, `isSubtask`), so the trace of a deleted task survives (`task.deleted` is true in the API); everything goes only when the project is deleted. `data` holds readable values ("from"/"to" names, not ids), so the history does not change if something is renamed later. Events of one edit share a timestamp: ordering is `createdAt desc, id desc` (no test notices if the `id` tie-break is removed).
- Tests: `activity.spec.ts` (diff), `test/activity.e2e-spec.ts`.
- **Front-end**: `/proyectos/[projectId]/actividad` (button "Actividad" on the board) and a "Historial" card at the bottom of every task/subtask detail (last 10). `lib/activity.ts` turns an event into the sentence in pieces (`describe`; the task title is a link while the task exists, plain text once deleted) and formats the time on the server (`toFeedItem`); `ActivityFeed` (client) shows the list and the "Ver más" button, which calls `loadActivityAction` with the cursor and appends the next page. The project's page has a **filter by person** (`?persona=<id>` in the URL, a select that applies on change, `actorId` in the API; combinable with `taskId`; the select lists current members, so a former member's events show in the unfiltered list but cannot be picked). Not done, on purpose: a filter by event type (nobody offers it, only requested; the 13 types are too fine for a select, it would need grouping into 4-5 categories). If the list gets noisy, the first step would be a single "Solo comentarios" option like Trello's, and drag & drop will force deciding which minor events to hide.

## Drag and drop (level 2)

- **`Task.position` (Float)** is the manual order inside a column of the board (top-level tasks only; subtasks ignore it and are listed by creation). **Priority and due date no longer sort the board**: they are just badges. The migration numbered the existing tasks with the old automatic order, so nothing visibly changed on day one.
- **A new task goes to the end of "por hacer"**, and so does a task that changes column without dragging (`PATCH` of `status`: the menu, the detail's select).
- **`PATCH /projects/:id/tasks/:taskId/move`** with `{ status, afterTaskId?, beforeTaskId? }` (the card right above / right below where it is dropped; none = top / end; both none = end). **The client never sends a position**: the server derives it from the neighbours (`position.ts`: middle point, `±1` at the ends), so a stale client cannot corrupt the order. Neighbours must be top-level cards of that column of the project (400 otherwise); subtasks cannot be moved (400); `DONE` with pending subtasks is the same 409 as in `update`. When the gap between two cards is too small to split (or the given neighbours are out of order) the column is renumbered 1..n and it tries again.
- **History:** a change of column records `STATUS_CHANGED`; reordering inside a column records nothing (noise, as in Trello). Any member can drag.
- **Front-end** (`@dnd-kit/core` 6.3 + `sortable` 10; not the newer `@dnd-kit/react` 0.x): the board page renders each card on the server and passes it as a node to `BoardColumns` (client), which only owns the *order* of the ids. Dropping updates the order at once and calls `dropTaskAction` (neighbours above/below; it revalidates the layout); if the API refuses (e.g. 409) the order goes back to the server's and the error shows above the board. The order shown follows the server whenever the server sends a different one (compared by a signature). Pointer needs a 6 px move to start (a click on the card, which is a link, stays a click; a click right after a drop is swallowed), touch needs a 250 ms hold, keyboard works (Space on the focused card). **Dragging is off with filters active (a hint says so) and on screens <= 900 px** (columns stack): there the card's "Mover a…" menu is shown; with dragging on, the menu is hidden by CSS (`[data-drag="on"] .moveMenu`). The detail page's status select always stays. `TaskCard` is now a plain `div`: the `li` is the sortable wrapper.
- **Guards against a stuck drag** (a native `<select>` popup swallows the mouse release, so dnd-kit kept the card glued to the cursor): `MoveSelect` stops pointer/touch/key events so the menu can never start a drag, the drag overlay hides the menu, and while a drag is on, a `pointermove` with no mouse button held cancels it (synthetic Escape).
- **Not verified in a real browser** (none was available when it was built): the drag itself, the touch hold and the keyboard. Only SSR output and the API were checked.
- Tests: `position.spec.ts`, `test/board-order.e2e-spec.ts` (checked with mutations: no renumbering, neighbours from any column, subtasks accepted as neighbours).

## Archived projects (level 2)

- **`Project.archivedAt`** (nullable). `POST /projects/:id/archive` and `/unarchive`: owner only (403 member, 404 outsider), idempotent (archiving twice keeps the first date). `ProjectView` carries `archivedAt`; `GET /projects` returns active and archived together (the front splits them).
- **Read-only = 409** ("El proyecto está archivado..."), enforced by `MembersService.requireWritableMember` / `requireWritableOwner` (they call `requireMember`/`requireOwner` first, so 404/403 win over 409; one extra query for `archivedAt`). **Every write path uses them**: create/update/move/delete of tasks and subtasks, create/edit/delete of comments, create/rename/delete of labels, add/remove members, `PATCH` of the project. New write endpoints must use the writable variants. Still allowed: every read, unarchive, and **deleting the project**. Not recorded in the activity log.
- **"Mis tareas" and the sidebar counter hide tasks of archived projects** (`project: { archivedAt: null }`).
- **Front-end:** `/proyectos` has Activos/Archivados tabs (`?archivados=1`, shown only when something is archived; `Segmented`); the sidebar lists only active projects. On an archived project the board shows an "Archivado" badge and a note and hides "Nueva tarea", dragging and the move menu; the task detail hides edit, status select, subtask check/create, the comment form and edit/delete, and delete; the members page hides add/remove; `/tareas/nueva` and `.../editar` redirect back. `/editar` (owner) shows only "Desarchivar" (`ArchiveButton`, no confirm dialog: reversible) while archived, and an "Archivar proyecto" card otherwise. The API is the source of truth: hiding in the UI is cosmetic.
- Tests: `test/archive.e2e-spec.ts` (every write refused, reads allowed, delete allowed, mis tareas, idempotence; checked with a mutation) and unit tests in `members.service.spec.ts` (the other service specs alias `requireWritableMember` to their `requireMember` mock). Not verified in a real browser: only the SSR HTML was checked with curl.

## Several owners (level 2)

Decided with the user: one mechanism covers both "several owners" and "transfer" (promote someone, then step down).
- **Any owner is equal.** `PATCH /projects/:id/members/:userId` `{ role: OWNER|MEMBER }` promotes a member or demotes an owner (also oneself); idempotent (same role = no change, no event). **There must always be at least one owner**: demoting or leaving as the last owner is a 409. `POST /projects/:id/leave` lets any member leave (tasks unassigned, comments kept, like a removal); the last owner cannot. Both are writes, so an archived project refuses them (409).
- **An owner cannot be removed directly** (403): demote first, then remove. Every owner-only rule (edit/archive/delete the project, members, labels, delete any task/comment) just uses `requireOwner`, so it already works with several owners.
- **Race guard:** `changeRole` and `leave` run in a transaction that first locks the project row (`SELECT ... FOR UPDATE`, `lockProject`) before counting the other owners, so two owners demoting each other at once cannot leave zero. Not covered by a concurrency test.
- Activity: new types `MEMBER_PROMOTED`, `MEMBER_DEMOTED`, `MEMBER_LEFT` (actor = who did it; for LEFT, the leaver).
- **Front-end** (members page): owners see "Hacer propietario" + "Quitar" on members and "Quitar propietario" on owners (only while there is more than one; it asks for confirmation, even for yourself, via `DemoteOwner`; promoting has no dialog); everyone gets a "Dejar el proyecto" card (the last owner sees why they cannot instead of the button). Leaving redirects to `/proyectos`.
- Tests: `test/ownership.e2e-spec.ts` (checked with a mutation: leaving as last owner), `changeRole` unit tests in `members.service.spec.ts`. Not verified in a browser.

## Invitations (level 2)

Decided with the user: invitations **replace** the direct add (`POST .../members` no longer exists, nobody is put in a project without accepting), only registered users, owners only, no expiry.
- **`Invitation`** (project, invited user, inviter; unique per project+user) **exists only while pending**: accept, decline and cancel delete it; accept also creates the MEMBER membership and records `INVITATION_ACCEPTED` (actor = the invited user) in one transaction. Sending/declining/cancelling record nothing.
- Backend `src/invitations/` (`InvitationsModule` imports `MembersModule`, `UsersModule`): `POST|GET /projects/:id/invitations` and `DELETE .../:invitationId` (owner only; invite/cancel are writes, so 409 on archived projects; 404 unknown email, 409 already member or already invited); `GET /me/invitations` (newest first, hides those of archived projects), `POST /me/invitations/:id/accept` (returns `{ projectId }`; 409 if the project got archived) and `/decline` (204). Someone else's invitation is a 404. Accept deletes the row first inside the transaction, so a double click joins once.
- **Front-end:** members page: "Invitar a alguien" form (`InviteForm`) and, for owners, a card of pending invitations with "Cancelar invitación"; `/invitaciones` (sidebar link with a counter, fetched by the layout through `getMyInvitations`) with Aceptar (goes to the project) / Rechazar. No email is sent: the invited user only sees it in the app.
- Tests: `test/invitations.e2e-spec.ts` (checked with a mutation: joining an archived project). The e2e fixture `createTeam` now joins its member through `addMember` (invite + accept). Not verified in a browser.
- **Planned for level 3 (decided): email sending**, so the invited person is told by email. Not decided: expiry, inviting unregistered emails (depends on the email sending), a role choice when inviting.

## Database environment (`bd_docker/`)

Docker Compose stack with two services:
- `postgres` (postgres:16-alpine, container `gestor_postgres`) — data in the `postgres_data` volume; has a `pg_isready` healthcheck.
- `pgadmin` (dpage/pgadmin4, container `gestor_pgadmin`) — depends on postgres being healthy; data in `pgadmin_data` volume.

Configuration comes from `bd_docker/.env` (`POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `POSTGRES_PORT`, `PGADMIN_EMAIL`, `PGADMIN_PASSWORD`, `PGADMIN_PORT`). Defaults: Postgres on 5432, database `gestor`, pgAdmin on 5050. `.env` holds credentials, so don't print or commit it.

Commands (run from `bd_docker/`):
- `docker compose up -d` — start the stack
- `docker compose down` — stop (add `-v` to also wipe the database volumes)
- `docker compose exec postgres psql -U admin -d gestor` — open a SQL shell

## Backend (`backend/`)

pnpm project, NestJS 12, **ESM** (`"type": "module"`): relative imports must end in `.js`, no `__dirname` (use `import.meta.dirname`). Tests use **Vitest** (`vi.fn()`, not Jest); lint is **oxlint**. `AGENTS.md` in `backend/` has NestJS-version notes from the CLI.

Commands (run from `backend/`; the DB stack must be up for anything touching Postgres):
- `pnpm start:dev` — run with watch; `pnpm build` then `node --env-file=.env dist/main.js` to run the build
- `pnpm test` — unit tests; single file: `pnpm test src/path/file.spec.ts`; `pnpm test:e2e` — e2e against a real Postgres (separate vitest config; needs the DB stack up, see "E2E tests")
- `pnpm lint`, `pnpm format`
- `pnpm db:migrate` (= `prisma migrate dev`), `pnpm exec prisma generate`, `pnpm db:studio`

Setup facts that are easy to miss:
- **Env**: `backend/.env` (gitignored; `.env.example` is the template) holds `NODE_ENV, PORT, FRONTEND_URL, DATABASE_URL, JWT_SECRET (>=32 chars, generated with `openssl rand -hex 32`), JWT_EXPIRES_IN`. Validated at boot by a **Joi** schema (`src/config/env.validation.ts`) passed to the global `ConfigModule` as `validationSchema`; the app refuses to start on invalid values. In `@nestjs/config` v12 `validationOptions` does not accept Joi options, so `abortEarly: false` lives on the schema itself. Read config through `ConfigService<EnvironmentVariables, true>`.
- **Bootstrap (`src/main.ts`)**: global prefix `api/v1`, global `ValidationPipe` (`whitelist`, `forbidNonWhitelisted`, `transform`, implicit conversion), CORS limited to `FRONTEND_URL`, shutdown hooks, Swagger UI at `/api/docs` (outside the prefix, Bearer auth declared). DTOs use class-validator / class-transformer.
- **Prisma 7**: config in `prisma.config.ts` (loads `.env` via `dotenv`), schema in `prisma/schema.prisma`, migrations in `prisma/migrations/`. The client is generated into `src/generated/prisma` (gitignored; `postinstall` runs `prisma generate`) — it must live under `src/` because `tsconfig.build.json` sets `rootDir: ./src`. Import it as `.../generated/prisma/client.js`. `PrismaService` (global `PrismaModule`) extends `PrismaClient` with the `@prisma/adapter-pg` driver adapter and connects on module init; inject it instead of instantiating clients. Keep `prisma` CLI and `@prisma/client` on the same version (pinned `7.10.1`).
- **bcrypt** is a native module: its build script is allowed through `pnpm.onlyBuiltDependencies` in `package.json`.

### Auth

- `JwtAuthGuard` is registered globally (`APP_GUARD` in `AuthModule`): **every route requires a Bearer JWT unless marked `@Public()`** (only `POST /auth/register` and `POST /auth/login` are public). New routes are protected by default; a new open route needs `@Public()`.
- `JwtStrategy.validate` loads the user by `sub` on each request (so a deleted user's token stops working) and sets `request.user = { id, name, email }`; read it with `@CurrentUser()`.
- `AuthService` hashes passwords with bcrypt (10 rounds) before calling `UsersService.create`, which stores whatever it receives. Wrong email and wrong password return the same 401 message. Responses never include `password`.
- Signing secret and expiry come from `JWT_SECRET` / `JWT_EXPIRES_IN` via `JwtModule.registerAsync` (the strategy reads the same secret to verify).
- Password rule lives in a single `@Matches` in `RegisterDto` (two `@Matches` on one property lose a message, since class-validator keys errors by rule type).
- `GET /auth/me` is not in the spec but is kept for good: the front-end's `(app)` layout and several pages use it to get the signed-in user (and a 401 there is how an expired token is detected).
- Names (`RegisterDto.name`, `CreateProjectDto.name`) are trimmed with a `@Transform` in the DTO, before `@IsNotEmpty()` runs, so a whitespace-only name is rejected. Services assume the DTO already trimmed. Because of the global `enableImplicitConversion`, a number sent for a string field (e.g. `"name": 123`) is accepted and stored as `"123"`; this was reviewed and left as is.

### Health

`GET /api/v1/health` (`src/health/`, `@Public()`) runs `SELECT 1` through Prisma: 200 `{status:"ok",database:"up"}`, or 503 `{status:"error",database:"down"}` with the real error only in the server log. No `@nestjs/terminus`. Use it as the API healthcheck when the API gets containerized.

### Projects and members

- **Dependency direction: `ProjectsModule` → `MembersModule` → `UsersModule`**, never the reverse. `MembersService` owns the `ProjectMember` table and exports `requireMember(projectId, userId)` / `requireOwner(...)`; both return the membership (so callers get the `role` for free) and throw. Tasks and comments should import `MembersModule` for the same checks instead of querying memberships themselves.
- **Non-members get 404, not 403** (`requireMember`), so a project's existence is not revealed. A plain member trying an owner-only action gets 403 (`requireOwner`).
- Routes: `/projects` (create, list mine, get, patch, delete) and `/projects/:projectId/members` (list, add by email, delete `:userId`; add/remove are owner-only). Every project response is a `ProjectView` (`role` of the caller + `memberCount`); members are flattened to `{ id, name, email, role }`.
- `ProjectsService.create` creates the project and its OWNER membership in one nested Prisma create (atomic, no dependency on `MembersService`).
- `MembersService.remove` unassigns that user's tasks and subtasks in the project and deletes the membership in one `$transaction` (`Task.assigneeId` points at `User`, so the DB does not do it). The owner cannot be removed (403), which also covers "owner cannot leave"; there is no separate leave endpoint.
- Emails are matched lowercased/trimmed in `UsersService`, but `AddMemberDto` uses `@IsEmail`, which rejects surrounding whitespace (400).
- Unit tests mock Prisma; the Prisma queries (ordering by role, `_count`, composite key `userId_projectId`, the transaction, cascades) are covered by the e2e tests (`backend/test/members.e2e-spec.ts`, `projects.e2e-spec.ts`).

### Tasks and board

- Routes live under the project: `GET /projects/:projectId/board`, `POST /projects/:projectId/tasks`, and `GET|PATCH|DELETE /projects/:projectId/tasks/:taskId`. `TasksModule` imports `MembersModule`; every method starts with `requireMember`, and lookups are scoped by `projectId` (a task id from another project is a 404).
- **`GET/PATCH/DELETE .../tasks/:taskId` serve tasks and subtasks alike** (both are `Task` rows); the response carries `parentId` (null for a regular task). Subtask creation and listing are separate: `POST|GET /projects/:projectId/tasks/:taskId/subtasks` (listing is oldest first; a subtask has its own assignee and copies `projectId` from its parent). Neither DTO has `parentId` and the global pipe forbids unknown fields, so a subtask cannot be moved nor a task converted (level 1). Moving a card between columns is a `PATCH` of `status`.
- Board = three columns (`TODO`, `IN_PROGRESS`, `DONE`, always present), only `parentId: null` tasks, ordered by `position` (manual order, see "Drag and drop"), then creation. Each card has `subtaskProgress {done, total}` computed from the subtasks. It also has `subtaskAssignees [{id, name}]` (level 2): the distinct assignees of its subtasks, oldest subtask first, unassigned ones skipped; every `TaskView` carries both.
- **`null` vs `undefined` in updates:** `description`, `dueDate` and `assigneeId` accept `null` to clear them; omitted means untouched. `title`, `priority` and `status` reject `null` (400). `@IsOptional()` lets `null` through, so non-nullable fields use `@ValidateIf(value !== undefined)` instead, and `UpdateTaskDto` redeclares them (`PartialType` would add `@IsOptional()` back).
- An assignee must be a project member (`MembersService.isMember`, non-throwing) or the request gets a 400. Delete: owner deletes any task, a member only the ones they created (403 otherwise).
- **Subtask rules live in `TasksService` (one service, same table):** creating a subtask under a subtask is a 400 ("Una subtarea no puede tener subtareas"); `PATCH status: DONE` on a task with any subtask not DONE (including IN_PROGRESS) is a **409** (the request is well-formed, the task's state conflicts); creating a subtask under a DONE parent, or reopening a DONE subtask (DONE -> any other status) while its parent is DONE, sets the parent to IN_PROGRESS **in the same interactive `$transaction`**. The parent is never completed automatically, and deleting subtasks never changes the parent. `update` always runs inside a `$transaction` (tests mock it by calling the callback with the same task mocks). Validation (assignee, level, 409) happens before the transaction, so a rejected request leaves the parent untouched. Rollback itself was checked once against Postgres with the `pg` adapter (a throw, and a real FK error P2003, after the parent update leave the parent as it was and create no subtask); concurrent requests are not guarded beyond that (read committed).

### Comments

- Routes: `POST|GET /projects/:projectId/tasks/:taskId/comments` and `PATCH|DELETE .../comments/:commentId`. They serve tasks and subtasks alike (both are `Task` rows). `CommentsModule` imports `MembersModule`; the task is checked with Prisma directly (no dependency on `TasksModule`).
- Check order in every method: membership (404 for outsiders) -> task belongs to the project (404) -> comment belongs to that task (404) -> permission (403). A comment id from another task or project is a 404.
- **Edit: author only, not even the owner (403).** Every edit sets `editedAt` (null until then) and keeps `createdAt`. **Delete: author, or the owner for any comment** (403 for another member).
- `content` is trimmed in the DTO, required, max 2000. `UpdateCommentDto` extends the create one (no `PartialType`: the text is always required). The thread is oldest first, no pagination. Responses carry `author {id, name, email}` and no `authorId`.
- Removing a member keeps their comments (history); `Comment.author` is `Restrict`, so deleting a user with comments is blocked by the DB.
- Covered by `comments.service.spec.ts` and `test/comments.e2e-spec.ts`, checked with mutations (owner editing, member deleting, missing task/project scoping, `editedAt`, thread order).

### Mis tareas

- `GET /api/v1/me/tasks?includeDone=true|false` (`src/my-tasks/`). Read-only, no dependency on `TasksModule` (it reuses its exported `taskInclude`/`toView` and queries Prisma directly).
- Returns tasks **and subtasks** assigned to the caller, in projects where they are still a member (the membership filter is defence in depth: removing a member already unassigns their tasks; a dedicated e2e deletes the membership directly to cover it). Each item is a `TaskView` plus `project {id, name}` and `parent {id, title} | null`.
- Default = TODO + IN_PROGRESS; `includeDone=true` adds DONE. Order: due date (none last), then priority (HIGH first), then creation. No pagination, no other filters (level 2).
- **`includeDone` is mapped by hand** in `MyTasksQueryDto`: with the global `enableImplicitConversion`, the string `"false"` would become `true`. Only `true`/`false` are accepted, anything else is 400 (covered by a DTO spec and an e2e).

### E2E tests

`pnpm test:e2e` runs `backend/test/*.e2e-spec.ts` (supertest against the real `AppModule`, same global setup as `main.ts` through `configureApp()` in `src/app.setup.ts`; no Swagger). Needs the Postgres container up and a `backend/.env` (only its `DATABASE_URL` is read).

- **Separate database, never the dev one.** `test/support/test-database.ts` derives the URL from `DATABASE_URL` by appending `_test` to the database name (`gestor` -> `gestor_test`), or uses `TEST_DATABASE_URL`. It **refuses any name that does not end in `_test`**, because the setup truncates every table.
- `test/global-setup.ts` runs once before everything: creates the database if missing (with `pg`), applies `prisma migrate deploy`, and truncates all tables except `_prisma_migrations`. It does **not** use `prisma migrate reset`: Prisma blocks destructive commands when it detects an AI agent, and that guard must not be bypassed. Data from the last run stays in `gestor_test` afterwards (handy to debug a failure) and is wiped at the next start.
- `vitest.config.e2e.ts` injects the app's env (`DATABASE_URL` of the test DB, a fixed fake `JWT_SECRET`, `FRONTEND_URL`...), which wins over `.env`, and sets `fileParallelism: false` (one shared database; files run one after another).
- Tests create their own data with unique emails and never depend on each other. Helpers: `test/support/app.ts` (`createTestApp`, `registerUser`, `api(app, user).get/post/patch/delete`, paths relative to `/api/v1`) and `test/support/fixtures.ts` (`createTeam` = project + owner + member + outsider, `createTask`, `createSubtask`).
- Decorators/DI work under vitest with Vite 8 as configured; no SWC plugin was needed.
- The suite was checked with mutations (inverting the board order, removing the 409 rule, allowing the owner to be removed, skipping the user check in `JwtStrategy`): each made exactly the relevant test fail. When adding a rule, prefer a test that would fail if the rule were removed.
- Not covered: concurrent requests, forced mid-transaction failures through the API (the rollback itself was checked once directly against Prisma), and load.

### Prisma schema decisions

- UUID ids everywhere; enums `ProjectRole` (OWNER/MEMBER), `TaskStatus` (TODO/IN_PROGRESS/DONE), `TaskPriority` (LOW/MEDIUM/HIGH, default MEDIUM).
- **Subtasks are a self-reference on `Task`** (`parentId` -> `Task.id`, relations `parent`/`subtasks`), deliberately not a separate table (decided over a separate `Subtask` table: same fields, one `Comment.taskId`, simple "mis tareas" query, level-2 move/convert is just changing `parentId`). Board queries must filter `parentId: null`.
- `Comment.editedAt` is null until edited.
- Cascades: project -> members/tasks; task -> subtasks/comments. `Task.assignee` is `SetNull` on user delete; `Task.creator` and `Comment.author` are `Restrict`.
- **Must be enforced in services, not the DB**: assignee is a member of the task's project (and removing a member must null their assignments in that project manually, since `assigneeId` points at `User`); a single owner per project; subtasks cannot have subtasks; a subtask copies `projectId` from its parent.
- Level-2 fields (archivedAt, task position, labels, activity log) are not in the schema yet; add them by migration.
